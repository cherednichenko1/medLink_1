## Оновлення 6 жовтня: реєстрація лікаря, записи з телефона та інтернет-доступ

Реєстрація лікаря тепер відкрита через `/registerPage?role=doctor`, без коду запрошення. Форма перевіряє дані, лікарню/спеціалізацію і пароль, зберігає хеш та створює початковий графік. Після реєстрації відкривається вхід лікаря. Новий обліковий запис не отримує автоматично доступ до чужих пацієнтів.

На сторінках профілю та історії, відкритих із QR, додано «Додати медичний запис як лікар». Гостя перенаправляє на вхід лікаря зі збереженням вибраного пацієнта. Форма `/doctor/patients/<id>/history` дозволяє додати діагноз, рекомендації та ліки з телефона. Доступ є лише у лікаря з записом пацієнта до нього або його попередніми медичними записами. Тимчасове посилання для перегляду не дає права редагування; пацієнт і сторонній лікар не можуть записувати дані. Записи з цієї форми самостійні, статус прийому не змінюють; для завершення прийому використовуйте розділ «Прийоми».

Діагностика: новий образ v1.0.2 і Wi-Fi IP уже були налаштовані, але на порту 8081 не працював port-forward. Після запуску `/livez` повернув HTTP 200. Адреса `192.168…` доступна тільки у локальній мережі. Для різних мереж підготовлено `scripts/internet-preview.sh`: тимчасовий Cloudflare HTTPS Tunnel, автоматичне налаштування PUBLIC_BASE_URL та Secure cookies, перевірка доступності, очищення лише власних процесів і повернення попередньої адреси при завершенні. Користувач окремо дозволив Cloudflare Tunnel для поточного MedLink після початкової відмови автоматичної перевірки. Спробу запуску виконано, але API api.trycloudflare.com недоступний з поточного інтернет-підключення: timeout із Mac і Docker, обидві офіційні IP 104.16.230.132 / 104.16.231.132. Публічної адреси ще немає. Скрипт перевіряє API перед запуском і показує помилку контейнера. Для повторної перевірки потрібна інша мережа або відновлення доступу до API.

Для застосування коду спочатку збережіть резервну копію БД за інструкцією нижче, потім:


Для запуску тимчасової інтернет-адреси ПІСЛЯ підтвердження публікації через Cloudflare:

```bash

```

Команда працює з Docker Desktop на Mac, використовує окремий контейнер `cloudflare/cloudflared` і локальний порт 8082. Якщо порт зайнятий іншим preview, спочатку зупиніть саме його. Cloudflare оброблятиме запити до застосунку, зокрема сторінки медичних даних після дозволеного входу або QR. Застосунок зберігає авторизацію, CSRF і перевірки доступу; проте публічна форма реєстрації лікаря також буде доступна з інтернету.

Скрипт надрукує `https://….trycloudflare.com`: відкрийте саме її на комп’ютері та телефоні, увійдіть заново й створіть новий QR. Телефон може використовувати 4G/5G. Попередні QR з локальною IP-адресою не працюватимуть поза Wi-Fi. Mac, Docker і термінал мають залишатися увімкненими; Ctrl+C зупиняє доступ. Після повторного запуску адреса зміниться. Cloudflare Quick Tunnels призначені для тестування без гарантії доступності; для постійного використання потрібна стабільна адреса/хостинг: https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/ .

Відкрийте адресу, яку надрукує скрипт, спочатку на телефоні вручну. Залиште термінал відкритим. Поза локальним тестуванням потрібен HTTPS.

Для лікаря є окремий вхід /doctor/login і навігація «Пацієнти», «Прийоми», «Розклад». Наявний лікар може входити зі своїм паролем. Адміністратор може створити нового лікаря через CLI з прихованим введенням пароля:

Лікар налаштовує тижневий графік, починає свій прийом після його запланованого часу, записує діагноз і рекомендації та завершує прийом. Медичний запис створюється один раз; доступ до чужих прийомів заборонений. Зміна графіка не видаляє раніше заброньованих прийомів.

## Історичне оновлення 1 жовтня 2026: QR та дизайн

- QR-коди тепер відображаються у спливному `dialog` через кнопку «Показати QR», SVG надсилається inline і не завантажується як файл. Вікно підтримує Escape, закриття за межами, повернення фокусу, стани завантаження та помилки.
- Гостьове відкриття звичайних приватних QR-сторінок перенаправляє на вхід із поверненням до вибраної сторінки після успішної авторизації. Дозволені лише внутрішні адреси профілю/історії; відкритих redirects немає. Дані інших пацієнтів залишаються захищеними.
- У вікні є **вимкнена за замовчуванням** опція «Дозволити перегляд без входу на 15 хвилин». Вона створює підписане тимчасове посилання лише після POST із CSRF та перевіркою прав. Профіль може поширити його власник; історію — власник або пов'язаний лікар. Для лікаря посилання показує лише його записи, а не всю історію.
- Посилання є bearer-доступом: людина з ним може переглядати вибрані дані протягом 900 секунд від створення. Не публікуйте QR. Закриття вікна/зняття галочки/вихід не відкликають уже видане посилання; дострокового відкликання в цій версії немає. Після спливу терміну нове завантаження відхиляється; уже переглянуті дані неможливо забрати з пристрою отримувача.
- Токен не містить самих медичних записів чи контактів. Підписаний payload містить ID і scope. Він передається у URL fragment, прибирається з адресного рядка й обмінюється POST-запитом: не потрапляє в звичайний URL access log. Сторінки повертають `no-store`, а тимчасовий перегляд — `Referrer-Policy: no-referrer`. Підроблені, некоректні та прострочені токени відхиляються. Для доступу поза локальною тестовою мережею потрібен HTTPS.
- Можлива друга причина недоступності з телефона — мережа: `localhost` телефону означає сам телефон, `medlink.local` зазвичай не налаштований у його DNS. Додано попередження в QR-вікні та `scripts/phone-preview.sh` для локального Kubernetes-перегляду через Wi-Fi IP комп'ютера. Скрипт не запускався й кластер не змінювався. Фактичну адресу/помилку телефона ще не отримано; реальне сканування слід перевірити після запуску.
- Оновлено головну, навігацію, пошук, профілі та кабінети у палітрі cream `#FFFAF0`, sky `#87CEEB`, blue `#4682B4`: картки лікарів, новий стартовий екран, м'які тіні, охайні форми, мобільне меню, статуси прийомів.

## Що змінено

### Реєстрація та вхід

- Виправлено адресу форми: POST `/registerPage` замість відсутнього `/submitRegistration`.
- Додано відповідні бекенду поля для пацієнта й лікаря, підтвердження пароля, серверну перевірку email, довжини полів, досвіду, РНОКПП і зовнішніх ключів.
- Нові паролі хешуються PBKDF2-SHA256 із 1 000 000 ітерацій. Існуючі відкриті паролі переводяться в цей формат одноразовою міграцією без зміни самого пароля.
- Вхід більше не порівнює пароль у SQL; використовується `check_password_hash`. Пробіли в паролі не обрізаються.
- Email нормалізуються; індекси забороняють дублікати без урахування регістру.
- Нові лікарі реєструються лише з кодом `DOCTOR_REGISTRATION_CODE`; без налаштованого коду самореєстрація лікарів закрита. Наявні лікарі збережені: адміністратор має перевірити, кому вже надано цю роль.
- Спроби входу та реєстрації обмежені PostgreSQL-лічильниками (до 10 спроб за 15 хвилин на обліковий запис/IP, спільно для всіх workers/Pod-ів). За nginx клієнтський IP читається через явно увімкнений `TRUST_PROXY`; за спільною зовнішньою адресою користувачі можуть ділити IP-ліміт.
- Помилки входу однакові для невідомого облікового запису та неправильного пароля. Перевірка невідомого облікового запису також виконує хешування.

### Захист запитів і персональних даних

- Усі POST/PUT/PATCH/DELETE перевіряють CSRF-токен. Вихід — лише POST.
- Вхід очищує попередню сесію та змінює CSRF-токен. Cookie має `HttpOnly`, `SameSite=Lax`, нове ім'я; термін сесії — 2 години. Користувачам потрібно увійти заново після оновлення.
- Замість відомого секрету за замовчуванням потрібен випадковий `FLASK_SECRET_KEY` від 32 символів. `SESSION_COOKIE_SECURE=true` вмикається для виключно HTTPS-сайту.
- Пацієнт бачить лише свої дані та історію. Лікар отримує доступ лише до пацієнтів із активним записом до нього або його попереднім записом у медичній історії; він бачить лише власні медичні записи.
- Ці правила діють для кабінету, персональної сторінки, історії, QR історії та PDF. Посилання/QR не надає додаткових прав.
- Додано CSP, заборону вбудовування сайту у frame, `nosniff`, `no-store` для нестатичних відповідей. Inline JavaScript перенесено у `static/forms.js`.
- QR-посилання використовують налаштований `PUBLIC_BASE_URL`, а не довільний Host із запиту.
- SQL-помилки не розкривають у відповідях адресу БД, пароль, SQL або дані користувача. Прибрано логування особистих даних при реєстрації/записі; з'єднання гарантовано закриваються після запиту.
- Запити до БД мають таймаути; розмір тіла HTTP-запиту обмежений 64 KiB. Debug вимкнено.

### Запис на прийом та інтерфейс

- Бронювання доступне лише пацієнту після входу. Це також виправляє змішування doctor ID та user ID, коли їх числові значення збігаються.
- Нові прийоми: майбутні будні, 09:00–16:30, інтервал 30 хвилин, горизонт до 90 днів, часовий пояс Europe/Kyiv. Це стандартний графік для поточної версії; індивідуальних розкладів/відпусток лікаря ще немає.
- Унікальний індекс PostgreSQL забороняє подвійний активний слот навіть при одночасних запитах. Конфлікт показує зрозуміле повідомлення.
- Пацієнт бачить свої записи та може скасувати власний майбутній прийом. Скасування зберігає запис зі статусом і звільняє слот.
- Кабінет лікаря показує майбутні прийоми та лише пов'язаних із ним пацієнтів.
- Пацієнт може переглянути свою історію й завантажити PDF. PDF отримав Unicode-шрифт для української, екранування тексту та перенесення довгих записів між сторінками.
- Повідомлення на сайті показують успіх/помилку реєстрації, входу, бронювання, скасування, додавання історії та виходу; мають доступні ролі `status`/`alert` і кнопку закриття.
- Форми пристосовано до вузького екрана, таблиці прийомів мають горизонтальне прокручування. Посилання на відсутні фото-заглушки замінено на піктограми.
- Опис платформи узгоджено з новими правилами запису й доступу.
- Email/SMS/browser push не підключалися: повідомлення реалізовані всередині сайту.

### База даних, продуктивність і розгортання

- `db.py` містить з'єднання, схему та міграцію; `security.py` — CSRF, валідацію, права та ліміти.
- Імпорт `app.py` не запускає міграції. Docker перевіряє конфігурацію та ініціалізує БД один раз перед Gunicorn.
- Транзакційний advisory lock серіалізує міграцію між репліками й автоматично звільняється при помилці. Таблиця `schema_migrations` запобігає повторній міграції.
- При помилкових старих датах, дублі слотів/email міграція відкочується повністю; дані не видаляються автоматично.
- Початкове наповнення більше не припускає `district_id=1`, використовує фактичний повернутий ID.
- Додано індекси історії та прийомів. Пошук показує до 50 лікарів на сторінці; зайняті слоти завантажуються одним SQL-запитом замість окремого запиту на кожного лікаря.
- Docker працює як non-root. Gunicorn використовує 2 workers для поточного ліміту пам'яті Kubernetes; PDF-шрифт і база часових поясів встановлюються в образ.
- Kubernetes отримав startup probe, окремі readiness `/healthz` і liveness `/livez`, non-root security context, заборону privilege escalation та скидання capabilities. Ліміт пам'яті застосунку — 384 MiB.
- Compose більше не містить фіксованого Flask secret/пароля БД: вони читаються з локального `.env`; додано `.env.example`.
- `.env` і дампи виключено з Docker build context; `*.dump` ігноруються Git. Секрети Kubernetes залишаються поза Git.
- Прямі та поточні транзитивні runtime-залежності оновлені й закріплені в `requirements.txt` для Python 3.12.
- Додано 33 тести й GitHub Actions: PostgreSQL-інтеграція, аудит залежностей і Docker build.

Тести без БД перевіряють CSRF, доступ гостей/ролей, cookie, ліміти запиту, валідацію часу/пароля/email, екранування PDF, повідомлення та приховування помилок. Частина перевірок використовує mock: вони не замінюють реальний запуск із PostgreSQL.

Тести з БД додані для реєстрації/входу, міграції старих паролів, rollback при дублях, повторних міграцій, бронювання/скасування, прямого SQL-конфлікту слотів, ліміту входу, доступу до чужої історії та повного сценарію пацієнт → лікар → історія. Вони запускаються з `TEST_DATABASE_URL` у власних тимчасових схемах.

## Що потрібно зробити перед білдом і перевіркою

Повний порядок і команди — у `DEPLOY.md`.

1. Резервна копія PostgreSQL.
2. Сильний `FLASK_SECRET_KEY` у власному Secret; за потреби код запрошення лікарів. Зберегти існуючі DB credentials.
3. Налаштувати `PUBLIC_BASE_URL` під фактичну адресу сайту/port-forward.
4. Для першої міграції зупинити старі Flask Pod-и, зібрати образ, застосувати новий deployment і перевірити rollout/логи. Старий образ не підтримує нові хеші паролів.
5. Пройти ручний сценарій із `DEPLOY.md` та виконати інтеграційні тести на окремій тестовій БД.

Поза цим оновленням залишаються: індивідуальні розклади лікарів, email-підтвердження та відновлення паролів, MFA, повний аудит медичних дій, налаштовані HTTPS/резервне копіювання/моніторинг для production. Поточний результат не є підтвердженням готовності до роботи з реальними медичними даними без цих операційних перевірок.
